## The folders

```text
apps/        things people open: web (FoldKit), docs (Fumadocs), cli, desktop, panels
contexts/    one package per bounded context, written with Alchemy Domain
adapters/    one package per vendor; the only place its SDK is imported
packages/    kernel (shared ids, errors, span names), ui, flags, schedule, conformance
services/    api: where a host, a telemetry backend and the adapters are chosen
infra/       Alchemy stacks
spec/        behaviour tests through the API only; never imports a context's src
tools/rules/ the lint and type rules, copied from rika-labs/rules
```

On this branch, `apps/docs`, `packages/kernel` and `tools/rules` exist. The other folders are planned, and `pnpm-workspace.yaml` already lists them as workspace globs.

Every internal package is named `@repo/<name>`. Packages are used as source: a package's `exports` point at its `src/*.ts` files, and there is no build step between packages.

## Which way dependencies point

```text
apps      ──▶ contexts, packages
services  ──▶ contexts, adapters, packages
infra     ──▶ services
adapters  ──▶ contexts (the port it implements), packages/kernel
contexts  ──▶ packages/kernel and other lib packages
kernel    ──▶ effect only
```

Two rules carry most of the weight:

- **A context never imports a service, an adapter, infra, an app or a host package.** A context that cannot import a host cannot come to depend on one, so swapping the host stays a one-line change.
- **Only `adapters/*` imports a vendor SDK.** A context declares a port, which is an Effect service. An adapter implements that port as a Layer, and a service picks which adapter to provide.

## How the direction is checked

Each package's `turbo.json` gives it a tag: `kernel`, `lib`, `context`, `adapter`, `service`, `infra`, `app` or `tooling`. The root `turbo.json` says which tags each tag may not depend on:

| Tag       | May not depend on                                      |
| --------- | ------------------------------------------------------ |
| `kernel`  | `lib`, `context`, `adapter`, `service`, `infra`, `app` |
| `lib`     | `adapter`, `service`, `infra`, `app`                   |
| `context` | `adapter`, `service`, `infra`, `app`                   |
| `adapter` | `service`, `infra`, `app`                              |
| `service` | `infra`, `app`                                         |
| `app`     | nothing may depend on an app                           |

`pnpm check` runs `turbo boundaries`, which fails when a package's dependencies break this table. Run it alone with:

```sh
mise exec -- pnpm boundaries
```

The `infra` and `tooling` tags have no rules yet.

## Adding a package

Copy `packages/kernel`: its `package.json` scripts, `tsconfig.json`, `vitest.config.ts` and `turbo.json`. Then set the tag in `turbo.json` to the kind of package it is. The tag is what puts the package under the rules above.

Each convention below is enforced by a check, and each section names it. When a check fails, its message says what to change.

## Every file names its role

Name every source file `<kebab-name>.<role>.ts`, such as `span-name.pure.ts` or `open-account.command.ts`. The role says what the file may hold and what it may import: a `.pure` file imports only other pure files and definitions, a `.service` exports one Effect service, and nothing imports a `.cli` or a test.

The full list of roles is in `tools/rules/src/oxlint/structure/roles.pure.ts`. Some roles are only allowed where `oxlint-structure.config.ts` turns them on:

- The Alchemy Domain roles (`aggregate`, `command`, `event`, `projection`, `policy`, `saga` and the rest) under `contexts/` and `packages/schedule/`.
- The FoldKit roles (`model`, `message`, `update`, `subscription`, `command`) under `apps/web/`, `apps/panels/`, `packages/ui/` and `packages/client-data/`.
- The `build` role in `apps/docs`, for code Next.js and Fumadocs run only while they build the site.

Next.js's own files (`page.tsx`, `layout.tsx`, `route.ts` and the rest) keep the names Next.js needs.

**Checked by** `lint:structure`, which runs `oxlint -c oxlint-structure.config.ts` over the whole repo.

## Tests mirror `src`

A test lives in its package's `tests/` folder, at the same path and name as the one `src/` file it tests, with `.test` added. `src/telemetry/span-name.pure.ts` is tested by `tests/telemetry/span-name.pure.test.ts`.

A test imports `describe`, `expect` and `it` from `@effect/vitest`. Each case is a named function, run with `it.effect` and `Effect.sync`, and a test never calls `Effect.run*`. A `describe` title is a phrase about the behaviour, not the name of a function:

```ts
import { describe, expect, it } from "@effect/vitest";
import { spanName } from "@repo/kernel/span-name";
import { Effect } from "effect";

const writesKebabCase = (): void => {
  expect(spanName("ledger", "OpenAccount")).toBe("ledger.open-account");
};

describe("a span name", () => {
  it.effect("writes a PascalCase operation in kebab case", () => Effect.sync(writesKebabCase));
});
```

Inside its own package a test imports the file it tests as `#src/telemetry/span-name.pure.js`. This example imports the kernel's public export instead, because the code blocks on this page are typechecked from `apps/docs`.

**Checked by** `lint:structure`, which refuses a file in `tests/` whose name does not name the role of a `src/` file, and by the `testing` lint rules. The `ratchet` tool in `tools/rules` also counts tests that sit outside the mirror; it is not in `pnpm check` yet.

## Imports

- Import your package's own source as `#src/<path>/<name>.<role>.js`. Relative imports also end in `.js`.
- Import another package through its `exports`, such as `@repo/kernel/span-name`, never through its `src` folder.
- `apps/docs` is the exception to the `.js` ending: Next.js and Node run its TypeScript directly, so it imports `.ts` and `.tsx` files by their real names.

**Checked by** `typecheck` and `lint:structure`.

## Functions with two or more parameters can be piped

An exported function with two or more parameters also has a pipeable form, built with `Function.dual`. Put the arity in a named constant:

```ts
import { Function as Fn, pipe } from "effect";

const withTaxArity = 2;

// Prices are whole cents, so the tax is rounded once, at the end.
const withTax: {
  (rate: number): (cents: number) => number;
  (cents: number, rate: number): number;
} = Fn.dual(withTaxArity, (cents: number, rate: number): number => Math.round(cents * (1 + rate)));

const direct = withTax(1000, 0.08);

const piped = pipe(1000, withTax(0.08));

export { direct, piped, withTax };
```

The kernel's `spanName` is written the same way, so both forms work:

```ts
import { spanName } from "@repo/kernel/span-name";
import { pipe } from "effect";

const direct = spanName("ledger", "OpenAccount");

const piped = pipe("ledger", spanName("OpenAccount"));

export { direct, piped };
```

**Checked by** `typecheck`: the `missingPipeableSignature` Effect diagnostic is an error.

## No inline suppressions

Do not write `oxlint-disable`, `eslint-disable`, `@ts-ignore`, `@ts-expect-error` or `@ts-nocheck`. A rule is turned off in one place only, the off table in `tools/rules/src/oxlint/base.config.ts`, with a reason next to it. If a rule is wrong for your code, change the code. If the rule is wrong, change it there for everyone.

Comments start with a capital letter and say why the code is the way it is, not what it does.

**Checked by** the pre-commit hook, which runs `file-fence` on the staged files. It also refuses a file over 500 lines.

## Every version lives in the catalog

A `package.json` never names a version. Add the version to the `catalog` in `pnpm-workspace.yaml` and write `catalog:` in the package:

```json
{
  "dependencies": {
    "effect": "catalog:"
  }
}
```

The workspace also sets these policies:

- **Strict catalog.** `catalogMode: strict` refuses a version written anywhere but the catalog.
- **Strict peers.** Peers are not installed for you. A package with tests lists `vite`, `vitest` and `@effect/vitest` in its own `devDependencies`.
- **A day's wait.** `minimumReleaseAge: 1440` refuses a release less than a day old. Pick the newest version that passes, and do not weaken the policy.

**Checked by** `pnpm install`, which applies the policies, and `sherif` in `pnpm check`, which checks the `package.json` files agree.

# Lifecycles are effect-machines

Status: accepted, 2026-11-07

Lifecycles such as the shard checkout, host, computer and deploy are `@typeonce/effect-machine` 0.46.0 definitions in `.machine.ts` files, and the planner runs only inside commands: a command in an `.actor.ts` file decodes the stored snapshot, checks `Machine.can`, runs `Machine.plan` and writes the encoded result inside its own transaction, and every entered state becomes a job and every published notice goes to the outbox. Nothing uses `Machine.start`, its timers or invokes, or `ClusterMachine`, so a machine never does I/O or keeps a process of its own. `role-imports` lets only `.machine.ts` and `.actor.ts` files import the root entry (`rolePackages` in `src/oxlint/structure/roles.pure.ts`) and only `.test.ts` files import `@typeonce/effect-machine/testing`, where `MachineTest.explore` checks invariants in every reachable state; every other role, and every other entry such as `unstable/cluster`, fails the rule. The base config loads `@typeonce/oxlint-plugin-effect-machine` at 0.46.0 with its `recommended` rules at error, so a clock read or a random value inside a transition fails lint as `no-nondeterministic-planning`. A `.machine.ts` file may name a property `data`, because the library takes transition data under that key: `taste/no-vague-names` checks declared names only (variables, parameters, functions, classes and types), never the keys of an object literal, so no `.machine.ts` override of the vague-name list exists.
